## 如何执行

1. 负责人从 Issue 的 `Reviewer:` 行确认审查人。审查人可提前阅读需求和已有代码；预分配不能允许任何被前置阻塞的实施提前开始。
2. 负责人完成验收检查并将 PR 标为 Ready for review 后，在 PR 右侧 **Reviewers** 请求本表指定的人。Issue 预分配与 PR 的实际审查请求是两步；未来 PR 不会仅因有本表而自动产生请求。
3. Reviewer 使用自己的账号，在独立目录检出 PR 最新提交，阅读 Issue、前置证据、完整 diff 和 PR 描述，重跑相关检查并核对代表性的异常情况。
4. Reviewer 记录被检查的 commit、命令、实际结果、发现的问题、未验证项和 AI 帮助。符合验收条件时由本人提交 Approve；需要修正时提交 Request changes。普通 Comment 不等于批准。
5. 代码、冲突解决或上游内容发生实质更新后，核对新的提交。Agent 可辅助分析、运行检查和起草意见，最终独立人工验证由组员负责。
6. 如指定 reviewer 是该变更的作者或实质共同作者、无法及时审查或缺少所需知识，负责人协调另一位独立组员，并同步 Issue 的 Reviewer 行、本表、路线图 #27 及 PR 的 Reviewers。原来未接受或未完成的审查不得写成已通过。
7. 合并、确认 Issue CLOSED 和下游开工仍按[合作说明](COLLABORATION.md)执行。审查分配不会自动关闭 Issue，也不会代替合并。
