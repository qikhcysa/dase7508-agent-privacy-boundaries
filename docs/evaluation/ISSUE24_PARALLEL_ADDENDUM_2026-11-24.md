# Issue 24 supplemental run: parallel execution addendum (2026-11-24)

This dated addendum supplements, without replacing, the frozen protocol
[`ISSUE22_2026-11-23.md`](ISSUE22_2026-11-23.md) for the formal supplemental
stage tracked by [Issue #24](https://github.com/qikhcysa/dase7508-agent-privacy-boundaries/issues/24).
It changes execution scheduling only. Prompts, tools, policies, synthetic
inputs, answer keys, grading criteria, the model and generation settings remain
exactly as frozen. The core run of Issue #23 was completed as a serial execution
period and is neither re-run nor re-graded. The single-operator supplemental
flow documented in [`ISSUE24.md`](ISSUE24.md) remains the protocol baseline.

## Scheduling change

- The frozen 240-attempt supplement plan is split into four fixture-aligned
  shards: `w1` B01-B03, `w2` B04-B06, `w3` B07-B09, `w4` B10-B12. A fixture has
  20 attempts, so each shard carries exactly 60 attempts.
- Fixture alignment is deliberate: a persistence pair stays inside one shard,
  and every shared H1 snapshot key (for example one fixture's benign and
  attacked pressure summaries) belongs to a single fixture, so no summary key
  is generated by two workers.
- The assignment, shard plans and their digests are frozen in
  `assignment.json` and the per-shard `classification.json` before the first
  provider request. A shard is never re-split afterwards.
- Every shard runs the same execution commit, model, settings, conditions and
  grading; each shard has one operator. Requests are never retried
  automatically, and a planned condition runs at most once in the union.

## Evidence and accounting

- Each shard owns its evidence root with the frozen shard plan, archived
  inputs, a copy of the inherited Issue 23 budget ledger, its own run ledger,
  attempt directories and snapshots.
- Each worker enforces the same daily 20 CNY, formal-stage 120 CNY and project
  500 CNY caps against its own copy. The coordinator sums the incremental
  conservative usage after merge and reconciles the provider dashboard; this
  report is recorded next to the merged evidence.
- The merge step refuses to complete unless every planned condition is recorded
  exactly once, re-checks reset evidence, and writes the owner's score report.
  Missing attempts, duplicates and cross-shard snapshot collisions are errors,
  not failures to be filled later.

## Reporting

- The supplemental results are reported as their own execution period and stay
  separate from the core estimates.
- The optional GLM-5.3-Flash summary cross-check is analysis support only and
  uses auxiliary settings; it never changes a formal attempt, a policy decision
  or a grading criterion. The exact summary text plus a teammate's reading
  remain authoritative.
- Raw bundles, traces and receiver records remain the source of truth for the
  independent exposure audit; merged evidence is a derived convenience.

## Change control

Any later change to prompts, tools, conditions, criteria, the sharding rule or
the attempt structure requires a new dated addendum. The previous version and
the affected shards are retained; the dated record is never overwritten.
